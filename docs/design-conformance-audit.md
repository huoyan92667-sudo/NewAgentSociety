# Agent 设计符合度核对

结论不是“完全符合”。当前核心架构已经按我们讨论的方向实现，但仍有明确未完成项。

| 我们确定的原则 | 当前实现 | 状态 |
| --- | --- | --- |
| 外层主模型理解整句话并自行选择工具 | 通用模型—工具循环和工具注册表已实现 | 已实现 |
| 餐厅推荐只是一个领域能力，不能控制整个 Agent | 完整推荐作为工具接入；普通闲聊可直接回答 | 已实现 |
| 查商家事实还是查评论，应由主模型判断 | 分成名称查找、事实查询、固定证据、长尾评论四类工具 | 已实现 |
| 完整推荐内部必须先融合、再硬过滤、再软排序 | 餐厅推荐工具内部固定顺序 | 已实现 |
| 本轮、会话、画像、场景按固定控制权融合 | 模型理解变化，程序固定来源覆盖顺序 | 已实现 |
| 硬条件负责排除，软偏好只负责排序 | 独立硬过滤与证据排序模块 | 已实现 |
| 软偏好按第一、第二优先级逐层比较 | 固定 14 项画像和排序器保留优先顺序 | 已实现 |
| 推荐必须给真实正反证据，没有证据就是未知 | 固定证据与长尾评论均保留原评论编号和原文 | 已实现 |
| 评论检索对上层隐藏关键词、向量等底层做法 | 上层只传商家编号和证据问题 | 已实现 |
| 会话可持久化，中断后可以恢复 | PostgreSQL 事件、状态版本和中断轮次已实现 | 已实现 |
| 长对话只带近期原话，旧内容总结后按需取回 | 最近轮次、工作记忆、摘要和搜索工具已实现 | 已实现 |
| 调用前检查参数，调用后记录耗时和词元 | 统一工具处理链和整轮统计已实现 | 已实现 |
| 地点应通过真实工具获得，而不是模型猜坐标 | 当前仍允许模型给近似中心 | 未实现 |
| 主模型最终回答应真正逐片返回 | 餐厅旧入口能分片，通用主模型仍未真正流式 | 未完成 |
| 高频 14 项应覆盖足够多商家 | 当前只离线覆盖 500 家 | 部分完成 |
| 测评应分别覆盖召回质量与 Agent 推荐回答质量 | 召回只有一个深标问题和 76 条逆向案例；回答正式集未建成 | 未完成 |
| 独立仓库应能从原始数据重建全部运行数据 | 在线源码独立，但离线生成入口未全部迁移 | 未完成 |
| 框架可以扩展旅游、酒店、景点 | 注册方式已具备，但尚无第二个真实领域 | 只有接口 |

因此准确说法是：**当前仓库符合我们确定的 Agent 核心运行方式，但还不是整个规划的最终
完成版。** 它已经不是写死问法的餐厅工作流；与此同时，地点工具、完整流式输出、正式
回答测评和离线数据可重建性仍然必须继续做。
