# 新 Agent 开发过程记录

本文档按时间记录新版 Agent 从混合工程中独立出来的全过程。这里不只记录最终功能，
也记录失败尝试、取舍、真实测试和未解决问题，避免后续只看到代码而不知道为什么这样做。

## 2026-09-03：启动独立迁移

### 修改前的问题

- 通用 Agent 位于 `src/yelp_agent/agent_platform`；
- 餐厅推荐位于 `src/yelp_agent/recommendation_v2`；
- 新代码仍引用旧模型调用、旧总配置、旧画像、旧向量和旧评论结构；
- 正式数据散落在根目录、源码目录和 Docker 数据目录中；
- 多个离线程序写死了本机绝对路径；
- 正式运行、训练、基准测试和临时产物没有完全分开。

### 本批目标

1. 建立 `new_agent` 独立项目根目录；
2. 先迁通用 Agent，再迁餐厅正式能力；
3. 通过独立配置消除写死路径；
4. 把正式运行、离线训练、基准测试和运行产物分开；
5. 在仅能看到新源码的环境里完成验证后，再处理旧位置的重复代码。

## 2026-09-03：源码与运行边界迁移

### 实际修改

- 通用模型调用、工具循环、调用前后检查、消耗统计、会话、工作记忆、旧话题摘要和
  PostgreSQL 持久化迁到 `src/new_agent`；
- 餐厅统一要求、六个场景、四路融合、硬过滤、商家事实、固定类别、500 家离线特征、
  评论证据和排序工具迁到 `src/new_agent/restaurant`；
- 删除正式流程对旧排序兜底的加载；固定 14 项直接读取离线画像，长尾要求才启动评论库；
- 建立唯一项目路径入口，取消正式源码中的开发机绝对路径；
- 新增语法树检查，后续一旦重新导入 `yelp_agent`，测试会直接失败；
- PostgreSQL 与 Qdrant 只保留根目录一份启动文件，不再在源码子目录各放一份。

### 数据整理

在线数据统一放到 `data/runtime`；训练数据放到 `data/training/review_judge`；召回测试放到
`data/benchmarks/review_retrieval`。逐文件校验得到：

| 内容 | 记录数 |
| --- | ---: |
| 餐厅事实 | 2,447 家 |
| 固定类别原始条目 | 319 个，其中 179 个可选择 |
| 完整评论 | 617,718 条 |
| 评论片段 | 624,746 个 |
| 用户画像快照 | 27,920 份 |
| 长期偏好信号 | 891,624 条 |
| 固定软偏好 | 500 家 × 14 项 = 7,000 项 |
| 固定软偏好证据关系 | 51,725 条 |

评论库没有直接复制正在运行的数据库目录，而是从评论片段和向量重新导入。这避免复制
过程中索引仍在写入而得到一个表面存在、实际损坏的库。

### 已完成验证

只把 `new_agent/src` 加入 Python 导入路径后，共收集到 152 条测试并全部通过，最近一次
耗时 4.78 秒。测试覆盖 Agent 工具循环、参数检查、消耗统计、上下文压缩、PostgreSQL、
四路融合、硬过滤、营业时间、评论召回、证据聚合和逐层排序。

### 过程中发现的问题

1. 第一次启动新 PostgreSQL 后立即执行升级时，容器仍处于初始化阶段；等待健康检查后
   重试成功。正式启动说明因此要求先等待数据库健康再升级。
2. 旧工程里的 54 MB 商家特征数据库被 Git 忽略，普通 Git 克隆拿不到；新项目加入
   运行数据校验入口，缺少它会明确失败。
3. 旧 Qdrant 集合名和端口带有旧目录含义；新项目改用自己的集合名和 6335 端口，旧库
   不再被默认读取。
4. 训练说明中仍有旧服务器命令。它们目前作为历史过程保存，下一批迁移离线生成程序时
   才会给出新的可执行入口，不能误当成当前在线启动命令。
5. 第一次从新目录运行命令行时没有先安装项目，Python 在调用模型前就报告找不到新包；
   执行 README 中的 `pip install -e .` 后解决。该失败与推荐逻辑无关。
6. 真实追问中，融合模型把 `search_center.radius_km` 填成空值，严格结构拒绝了整轮。
   现在结构错误会连同固定输出格式退回模型一次，由模型保持语义不变自行修正，程序不
   猜半径。新增回归测试后总测试数为 152 条。

## 2026-09-03：独立数据库与评论检索库完成

### PostgreSQL

新项目使用自己的 PostgreSQL 容器、数据目录和 5434 端口。三份数据库升级全部执行，
当前版本为 `0003_turn_index`。真实测试的用户消息、模型回答、工具调用、用时、词元、
餐厅要求版本和当前工作记忆都写入新库，不再使用旧 Agent 数据库。

### Qdrant

没有重新计算 624,746 个评论片段的向量。程序读取已经生成的片段和 1024 维向量，写入
新项目自己的 `new_agent_review_segments_v1` 集合，并同时建立关键词索引。导入后：

- 实际记录数：624,746；
- 商家编号索引：624,746 条；
- 评论编号索引：624,746 条；
- 评论时间索引：624,746 条；
- 导入清单中的片段、向量文件指纹与数据校验清单一致。

过程中发现数据校验程序会固定把 `qdrant_ready` 重写为 `false`。实际评论库没有丢，
只是清单误报。现在校验程序会读取导入清单，核对片段指纹、向量指纹和条数后自动决定
是否就绪，不再覆盖正确状态。

### 长尾检索后端实测

限定 Alpen Rose，查询“着装随意、不需要穿正装”。4 条正反说法的本地向量化用时
2.327 秒，向量和关键词并行检索用时 0.379 秒，完整评论恢复用时 1.523 秒，共得到
23 条去重评论。最高正向相似度 0.487，未达到 0.60 的证据门槛，因此 23 条全部标为
模糊、最终保持未知。这个结果验证了评论工具不会因为单条关键词命中就强行作出结论。

完整 DeepSeek 验证在请求发出前被本地权限审核服务以 HTTP 404 阻断，所以没有产生
模型调用和数据库写入。后端检索已经完成验证，主模型自主选择工具仍需补测。

## 2026-09-04：断机恢复与长尾真测收口

### 断机恢复检查

Docker 关闭后，Qdrant 和 PostgreSQL 都无法连接，但数据目录仍分别保留约 4.46 GB 和
49 MB 文件。重新启动原容器后，没有执行重建或重新导入：PostgreSQL 仍在最新的
`0003_turn_index` 版本；Qdrant 恢复为绿色，实际记录数仍为 624,746，三个筛选字段的
索引条数也全部一致。昨天的 6 轮会话、73 条事件和 11 次模型调用全部存在。

### 第一次长尾真测暴露的问题

主模型正确识别第三家 Alpen Rose，并选择 `search_business_review_evidence`。最终回答
正确说明没有着装证据，但同一工具执行了 3 次：前两次分别因为内部模型漏项和非法 JSON
失败，第三次才进入评论检索。整轮耗时 83.78 秒、输入 24,043 个词元。

### 修复与复测

检索说法的结构错误现在在工具内部修正一次，外层不再重跑完整工具；工具参数说明也明确
禁止把一件问题的正反方向拆成两项。新增回归测试后共 153 条测试。

真实复测只调用 1 次评论工具，总耗时 29.86 秒、输入 11,355 个词元。回答仍明确表示
正反证据均为空，不能断言餐厅允许或禁止休闲装。这个结果同时保留了谨慎性并消除了两次
昂贵的外层重试。
