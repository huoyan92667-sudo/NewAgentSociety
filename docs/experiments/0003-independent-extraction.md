# 实验 0003：新 Agent 独立目录验证

## 修改前

通用 Agent、餐厅推荐、旧排序、总配置和数据路径混在 `yelp_agent` 包中。新版模块仍有
8 个文件引用旧模型封装、9 个文件引用旧总配置，多个程序写死开发机绝对路径。即使
功能能跑，也无法证明离开旧 Agent 后还能运行。

## 修改后

- 新源码全部位于 `new_agent/src/new_agent`；
- 配置、运行入口、数据库升级、正式数据、训练数据、测评与历史文档都有独立位置；
- 新源码对旧 `yelp_agent` 的导入数为 0；
- 默认在线数据路径全部在 `new_agent/data/runtime` 下；
- PostgreSQL 使用独立容器和 5434 端口；Qdrant 使用独立容器和 6335 端口；
- 自动测试只把 `new_agent/src` 加入导入路径。

## 离线验证

2026-09-03 首次收集并执行 152 条测试，全部通过，耗时 4.78 秒。其中餐厅能力
增加了一条“模型修正非法结构”的回归测试。2026-09-04 长尾真测暴露检索说法格式
错误后，又增加一条工具内部修正的回归测试，当前总数为 153 条。

数据校验结果：2,447 家餐厅事实、319 个原始类别、617,718 条完整评论、624,746 个
评论片段、5,000 个用户的 27,920 份画像快照、891,624 条偏好信号，以及 500 家餐厅
的 7,000 项固定软偏好分与 51,725 条证据关系。

现有 624,746 个片段和 1024 维向量已经全部导入新项目自己的 Qdrant 集合
`new_agent_review_segments_v1`。这一步没有重新生成向量，而是复用已经核验过的向量，
重新建立新项目自己的向量索引、关键词索引以及商家编号、评论编号和评论时间筛选字段。
导入后从 Qdrant 接口读取到的实际记录数仍为 624,746，导入清单中的两份文件指纹与
正式数据校验清单一致。

## 第一轮真实独立验证

真实用户 `ET8n-r7glWYqZhuR6GcdNw`，独立会话
`new-agent-independent-20260903`：

1. “给我推荐一家安静，服务好，停车方便的牛排店”：模型主动调用完整推荐。牛排类别
   从全部餐厅筛到 13 家，但用户没写到店时间，系统按当时上午 10:16 的“当前营业”
   默认值把 13 家全部过滤。整轮 13.59 秒，输入 7,727、输出 1,413。
2. “不用现在营业，我明天晚上 7 点去”：首次返回的搜索半径为空，严格结构拒绝；加入
   一次模型自我修正后原样重试成功。12 家进入排序，固定前五为 Barry's Steaks、
   Barclay Prime、Alpen Rose、Picanha Brazilian Steakhouse、Broncos Brazilian
   Steakhouse。整轮 23.61 秒，4 次模型调用，输入 18,498、输出 3,070。
3. “第三家的服务怎么样”：工作记忆正确把第三家解析为 Alpen Rose，只调用固定软偏好
   证据工具，工具耗时 10 毫秒，没有重跑推荐。整轮 10.70 秒。
4. 临时询问煎牛排撒盐：直接回答，没有调用餐厅工具；随后问“回到刚才的餐厅，第三家
   地址和评分”，仍正确找到 Alpen Rose，只调用商家事实工具，工具耗时 0.5 毫秒。

这组结果证明源码、数据库恢复、四路推荐、单店追问、闲聊切换和对象指代都能从新目录
独立工作。也暴露两个未解决问题：主模型最终回答仍是主要耗时；命令行传入 `--stream`
时主模型还没有真正逐片返回，`first_answer_delta_ms` 仍为空。

## 长尾评论检索后端验证

在新 Qdrant 完成后，限定第三家 Alpen Rose 的真实编号，查询“着装随意、不需要穿
正装”。验证时人工给出两条支持说法和两条反对说法，目的是只检查本地向量、关键词、
完整评论恢复和证据门槛，不调用外部大模型：

- 4 条查询说法在 1 个批次中完成向量化，用时 2.327 秒；
- 向量与关键词混合检索墙钟时间 0.379 秒，其中向量路线 0.303 秒、关键词路线
  0.345 秒，两路并行；
- 从片段恢复 23 条去重后的完整评论，用时 1.523 秒；
- 关键词路线确实找到了“elegant yet casual 5-star experience”这条相关片段；
- 但全部 23 条评论的正反差异都未达到接受门槛，最高正向相似度只有 0.487，低于
  0.60，最终全部归为模糊证据，聚合分保持 0.5（未知），没有编造着装规定。

这说明独立评论库、按商家过滤、两路召回、完整评论恢复和保守证据判定都能运行；也说明
关键词命中不等于可以直接下结论，仍必须经过语义相关度和正反差异检查。

## 长尾评论完整真测与修复

获得用户明确授权后，沿用同一会话询问第三家 Alpen Rose 是否允许休闲装。主模型正确
选择了实时评论工具，最终也正确回答“正反证据都是 0，不能判断”。但第一次真测连续
调用了同一工具 3 次，总耗时 83.78 秒、输入 24,043 个词元，不应视为合格结果。

数据库事件证明三次调用并非完全相同的盲目重试：第一次工具内部生成检索说法时漏掉
一项要求；第二次返回的 JSON 缺少分隔符；第三次才成功。原实现把内部格式错误直接返回
给外层主模型，外层只能重新调用整个工具，重复发送约五千词元的会话上下文。

修复内容：

- 长尾检索说法出现漏项或非法 JSON 时，由工具内部携带精确错误和全部要求编号修正一次；
- 修正提示禁止合并、删除、增加或改名要求；
- 工具字段明确规定“一项是一件完整问题”，同一问题的正反方向不能拆成两项；
- 首次生成和修正调用的词元都进入总统计，不能因内部修正而少记成本；
- 新增回归测试，先确认旧实现失败，再确认修复后通过。

修复后用同一授权范围重新真测：

| 指标 | 修复前 | 修复后 |
| --- | ---: | ---: |
| 评论工具调用 | 3 次 | 1 次 |
| 全部模型调用 | 8 次 | 3 次 |
| 输入词元 | 24,043 | 11,355 |
| 输出词元 | 1,665 | 691 |
| 工具耗时 | 65.30 秒 | 21.84 秒 |
| 总耗时 | 83.78 秒 | 29.86 秒 |

修复后仍没有召回可用于判断着装要求的评论。最终回答明确区分“没有可用证据”和“商家
允许休闲装”，没有把检索不到写成肯定结论。约 20 秒的剩余工具耗时主要是命令行每次
新进程冷启动本地向量模型；长期运行的服务会在第一次加载后复用该模型。

完整机器输出保存在本地 `runs/independent/`，按规则不提交 Git；本文保存可复查的输入、
关键输出和数字。
